  Use whenever debugging a bug report, test failure, or flaky/intermittent, environment-dependent,
  timing, concurrency, or resource-contention issue. ALSO use any time you're about to edit
  implementation code in response to an observed failure, before the root cause is confirmed.
  Enforces stating a falsifiable, cheaply-checkable prediction BEFORE touching implementation
  (direct cheap check, or a minimal state-machine model check for ordering/exclusion bugs), then
  sizing the fix to the confirmed depth of the cause. Prevents two failure modes: many small patches
  on unconfirmed symptoms (root-cause debt), and large speculative rewrites on unverified guesses
  (wasted effort, new failure modes). Trigger proactively, unasked, before proposing any fix for a
  bug not yet confirmed with cheap evidence.

# Diagnose Before Fix
 
## 核心原則
 
行動の規模は、診断の確信度に比例していなければならない。確信度が低いまま行動の規模だけ大きくしたり小さくしたりしてはいけない。
 
- 確信度が低いのに修整だけ小さくごまかす → 症状パッチが積み重なり、根本原因が温存されたまま負債になる
- 確信度が低いのに修整だけ大きく作り直す → 仮説が外れていた場合、無駄打ちの上にさらに別の壁にぶつかる
説明の「もっともらしさ」は、その説明が正しい確率とは無関係である。複数の症状が1つの原因で綺麗に説明できるという感覚(エレガンス)は、仮説を思いつく動機にはなっても、仮説が正しいことの証拠にはならない。これに気づかず確認を飛ばして実装に進んではならない。
 
モデル検査や形式証明による確認は、モデルについての証拠であって、直ちに実装上の根本原因確認にはならない。反例や証明の失敗は、モデルの仮定・遷移規則・網羅性に依存する。反例が見つかった場合も、その経路が実装でも実際に到達可能であることを別途確認して初めて、根本原因確認済みとして良い。
 
## 絶対原則: 実装ファイルを編集する前のゲート
 
観測された不具合に対して**振る舞いを変える**実装コードを変更しようとする前に、必ず以下の3点を満たすこと。満たしていない場合、振る舞いを変える変更を開始してはならない。
 
1. 仮説を1つ、明示的に言葉にする
2. その仮説が正しければ「実装を変更しなくても観測できるはずの具体的な予測」を1つ以上、言葉にする(再現手順、ログの特定の値、既存メトリクス、ツールでのstate確認など)
3. その予測を、振る舞いを変える変更をする前に検証する
やむを得ず予測を検証しないまま振る舞いを変える場合は、その旨を出力フォーマット(下記)で明示すること。隠して進めてはならない。
 
### 診断用の変更はこのゲートの対象外(ただし要注意)
 
ログ追加・assertion追加・tracing span追加・状態ダンプ・fault injection hookなど、**振る舞いを変えないことを意図した**診断用の計装は、このゲートの対象外である。これらはむしろ「安く検証する」(ステップ2A)ための手段として積極的に使ってよい。既存の観測性が低いシステムでは、こうした計装無しに安価な検証は成立しない。
 
ただし、診断用の変更であってもタイミングを変え、競合や再現条件を隠すことがある(観測者効果)。その場合は、それが診断目的の変更であることと、振る舞いに影響しうる可能性を明記すること。
 
## ワークフロー
 
### ステップ1: 仮説と予測を立てる
 
症状を観測したら、まず仮説を立てる。同時に、それが「安く直接確認できる性質」か「順序・排他・前提条件の噛み合わせのような構造的性質」かを判定する。
 
- 前者(例: 特定の値、特定の状態、既存ログで判別できる) → ステップ2Aへ
- 後者(例: 競合状態、デッドロック、初期化順序、リソース解放漏れ) → ステップ2Bへ
### ステップ2A: 安価に検証する
 
実装を変えずに確認できる方法(ログ確認、既存のstate/デバッグツール、ドキュメント参照、既存テストの実行、必要なら診断用計装の追加、ユーザーへの事実確認など)で予測を検証する。
 
結果は3通りに分類する。
 
- **支持**(予測通りだった) → 根本原因確認済みとしてステップ4へ
- **反証**(予測と食い違った) → ステップ3へ
- **判定不能**(ログ不足、再現せず、環境差など、当たったとも外れたとも言えない) → ステップ2Fへ。**この場合、仮説を棄却してはならない。**
ユーザーに尋ねる場合は、**検証可能な事実だけを尋ねること**。「原因は何だと思いますか」のように診断そのものを尋ねてはならない。それは検証ではなく、未検証の仮説をユーザーの直感にすり替えているだけである。尋ねてよいのは「Xという状態か」「Yという前提は成り立つか」のような、Yes/Noまたは具体的な値で答えられる質問に限る。
 
### ステップ2B: 既存の形式仕様があるかを確認する
 
構造的な性質(順序・排他・前提条件の噛み合わせ)を疑う場合、いきなり新規モデルを組んではならない。
 
まず、race detector・thread dump・lock graph・profiler・既存の監視メトリクスなど、モデル検査より安価に手がかりが得られる手段が使える場合は、それらを先に試す。モデル検査(既存仕様の利用・新規構築のどちらも)は、それらでは判別しにくい性質――希少なinterleaving、まだ発生していない経路についての安全性・活性など――を扱う場合に選ぶ。
 
そのうえで、その部分を扱う既存の形式仕様(Lean証明、TLA+仕様、model checker用の既存モデルなど)が既にあるかを確認する。あれば、それを参照するか、必要な性質を追加して検証する方が、ゼロから即席モデルを組むより安く正確である。
 
既存の形式仕様が無い場合のみステップ2Cへ。既存の形式仕様がある場合は、それを使ってステップ2Dへ進む。
 
### ステップ2C: 最小モデルを新規に組んでモデル検査する
 
対象の実装コード全体をモデル化しようとしないこと。疑っている性質だけを、できるだけ少ない状態と遷移に絞って書く。目安として数個程度だが、これは上限ではない。世代番号・retry回数・bounded queue・lease期限のような性質を扱う場合は、それより多くなってもよい。
 
全状態を機械的に探索し、ゴールに到達しない経路(反例)があるかを確認したら、ステップ2Dへ進む。
 
モデルの構築や検査そのものが想定より時間がかかると分かった場合は、無理に続けず、ステップ4の「症状レベルの理解しか得られなかった場合」に切り替えてよい。これはステップ1直後の時間切れ判断と同じ扱いである。
 
### ステップ2D: 反例の実装対応を確認する
 
モデル検査や証明の結果だけでは、実装上の根本原因確認にはならない。結果を次の3通りに分類する。
 
- **反例あり、かつ実装でも到達可能**: その経路が実装でも実際に起こりうることを、トレース・再現・計装・fault injectionのいずれかで確認できた場合。→ 根本原因確認済みとしてステップ4へ
- **反例なし(全状態を網羅的に探索完了)**: モデルの仮定が妥当という前提のもとで、この構造的性質は原因ではないと言える。→ ステップ3へ
- **判定不能**: 反例はあるが実装での到達可能性を確認できていない/確認する手段がない、または証明が完了しない(タイムアウト・補題不足・帰納法の選択ミスなど)、または探索が網羅的でない場合。これらは「反例なし」とは異なり、命題が偽であることの証拠にはならない。→ ステップ2Fへ。**この場合、仮説を棄却してはならない。**
証明が失敗したことと反例が見つかったことを同一視しないこと。前者は多くの場合、命題の真偽について何も語らない。
 
### ステップ2F: 判定不能を扱う
 
判定不能は反証ではない。仮説を棄却してステップ1に戻ってはならない。代わりに、検証方法や観測点を見直し、同じ仮説のままステップ1の分岐(安く直接確認できるか/構造的性質か)からやり直す。
 
同じ仮説で何度検証しても判定不能が続き、かつ時間や材料の制約でこれ以上続けられない場合は、ステップ4の「症状レベルの理解しか得られなかった場合」に切り替えてよい。
 
### ステップ3: 仮説を棄却し、記録する
 
ステップ2Aの「反証」、またはステップ2Dの「反例なし(網羅的に探索完了)」となった場合、その仮説は会話やコミットメッセージ上に明示的に棄却として残す(例:「〜という仮説を検証したが反証された」)。同じ仮説を形を変えて再度提案しないこと。ステップ1に戻り、新しい仮説を立てる。
 
これは「実際に仮説を検証して反証された」場合専用である。判定不能(ステップ2F)や、修整後に症状が再現した場合(ステップ6)は、仮説が本当に一度も検証されていないケースも含むため、ここには当てはまらない。両者を混同しないこと。
 
### ステップ4: 修整の規模を、確認できた深さに合わせる
 
- **根本原因が確認できている場合**: その原因に見合った規模の修整を行ってよい。原因が構造的であれば、確認に使ったモデルの精緻化として実装を書き直すことも許される。
- **時間や材料の制約で、症状レベルの理解しか得られなかった場合**: 修整は症状に対する最小限のものに留める。かつ、コードコメント・コミットメッセージ・ユーザーへの報告のいずれかで「根本原因未確認・暫定パッチ」であることを明示し、後で根本原因を追うためのフォローアップ(TODOコメント、issue起票など)を残す。これを省略してはならない。
### ステップ5: 修整後に再検証する
 
修整して終わりにしない。ステップ2A/2B/2C/2Dで使った検証手段(モデル検査の再実行、再現手順の再実行、既存テストの実行)を修整後にもう一度行い、症状が本当に消えたことを確認してから完了を報告する。症状が再現した場合はステップ6へ進む。
 
### ステップ6: 修整後も症状が再現した場合
 
無条件に「元の仮説を棄却」してステップ1へ戻ってはならない(それはステップ3の役割であり、ここでは意味が異なる)。まず、ステップ4でどちらの経路を通ったかを思い出す。
 
- **根本原因を確認済みの上での修整だった場合**: 元の仮説(構造的な原因の特定)自体は事実やモデル検査によって裏付けられていた可能性が高い。まずは「実装がモデル/仕様の結論を正しく反映していたか」「他の独立した要因が重畳していないか」を疑うこと。診断そのものが誤っていたと即断しない。
- **根本原因が未確認のまま暫定パッチを当てていた場合**: そもそも仮説は一度も検証されていない。症状が再現したこと自体は驚くことではなく、単純にステップ1へ戻り、根本原因の特定を継続する。
いずれの場合も、次の仮説を立てる際にステップ1へ戻る。
 
## 出力フォーマット
 
実装コードの変更(振る舞いを変えるもの)を提案する際は、必ず次の3行を先頭に明示すること:
 
```
仮説: <一文>
予測(検証方法): <一文>
検証結果: 支持 / 反証 / 判定不能 / 未検証(暫定対応)
```
 
## 定量的な性能問題について(補足)
 
レイテンシやスループットなど「どれくらい遅いか」という量的な性質は、このスキルが扱う離散状態のモデル検査では検証できない。これらは事前見積り(キューイング理論など)・常時計装・CIでのレイテンシ回帰ゲートという別の手段で扱うべきであり、無理に本スキルの状態機械モデルに押し込めようとしないこと。
 
## 例
 
**Bad(症状への場当たり的パッチ)**
> ログにnullが出ていたのでnullチェックを足しました。
 
→ なぜnullになるのかの仮説も予測も無いまま、末端に継ぎ木している。
 
**Bad(未検証の根こそぎ書き直し)**
> このアーキテクチャ自体に問題がありそうなので、該当モジュールを設計から書き直しました。
 
→ 仮説はあるが、実装を変える前に安く検証した形跡が無い。外れていた場合の被害が大きい。
 
**Good(直接確認で支持)**
> 仮説: AudioContextがsuspendedのままでcurrentTimeが進んでいない
> 予測(検証方法): devtoolsで`audioContext.state`を見れば`"suspended"`のはず
> 検証結果: 支持 → resume()の呼び出し位置(ユーザー操作ハンドラの外)を修整し、修整後に再度state確認して`"running"`になることを再検証した
 
**Good(判定不能を棄却せず扱う)**
> 仮説: 共有デコーダの解放漏れ
> 予測(検証方法): ヒープダンプでデコーダインスタンス数が時間とともに増え続けるはず
> 検証結果: 判定不能 → 本番環境でのみ発生し、ローカルではヒープダンプが取れなかった。仮説は棄却せず、次は本番向けの軽量計装(定期的にインスタンス数をログ出力)に切り替えた
